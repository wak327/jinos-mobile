# OpenHarmony / HarmonyOS NEXT: what is genuinely novel and borrowable

Status date: 2026-10-02. Everything below was checked against 2024-2026 primary sources (OpenHarmony docs on GitCode/Gitee, the OSDI'24 HongMeng paper, Eclipse Oniro posts and FOSDEM 2025/2026 slides, Wikipedia for dated release facts). Items I could not verify are marked **unverified**.

The single most important framing fact: **"HarmonyOS NEXT" and "OpenHarmony" are two different operating systems that share upper layers.** OpenHarmony (Apache-2.0, OpenAtom Foundation) ships on Linux 5.10/6.6 or LiteOS. HarmonyOS NEXT / HarmonyOS 5 and 6 (Huawei, proprietary) ships on the closed-source HongMeng microkernel and is only available on Huawei hardware with locked bootloaders. Most of the "no Linux, no Android, microkernel" marketing refers to the closed product, not the open project.

---

## 1. Architecture

### 1.1 Layers (OpenHarmony, the open project)

Four layers, bottom-up (OpenHarmony overview; reproduced in Oniro's FOSDEM 2026 deck):

1. **Kernel layer**: a Kernel Abstraction Layer (KAL) over three kernels: LiteOS-M (mini systems, MCU, >=128 KiB), LiteOS-A (small systems, MMU, >=1 MiB) and Linux (small and standard systems, >=128 MiB). The Linux baseline is LTS 4.19/5.10 with 6.6 adapted for the RK3568 reference board. The **driver subsystem (HDF)** sits in this layer. ([kernel overview](https://gitee.com/openharmony/docs/blob/master/en/device-dev/kernel/kernel-overview.md), [kernel readme](https://gitcode.com/openharmony/docs/blob/master/en/readme/kernel.md))
2. **System service layer**: distributed scheduler, distributed data management, DSoftBus, the Ark multi-language runtime, security (AccessToken, SELinux policy, HUKS), graphics (Rosen render service), multimedia, telephony, AI, plus hardware-service subsystem sets (location, IAM, wearable, IoT).
3. **Framework layer**: ArkUI, the Ability framework (Ability Kit / Stage model), application framework.
4. **Application layer**: system apps and third-party HAPs (Harmony Ability Packages).

### 1.2 How hardware is reached on the Linux-based "standard system"

This is the part that matters most for a phone OS, and it is less exotic than the marketing suggests.

- **You cannot run vanilla mainline.** OpenHarmony's Linux kernel needs `CONFIG_ANDROID_BINDER_IPC` (IPC backbone), `CONFIG_ASHMEM` and `CONFIG_PURGEABLE_ASHMEM` (it has not migrated to memfd yet), `CONFIG_DRIVERS_HDF`, `CONFIG_ACCESS_TOKENID` (the security token is kernel-visible) and `CONFIG_SCHED_RTG` (related thread groups). Source: Oniro PMC lead Francesco Pham, FOSDEM 2026, slide 6 ([slides PDF](https://archive.fosdem.org/2026/events/attachments/SYBWKY-bringing_openharmony_to_phones_lessons_from_the_oniro_porting_effort/slides/266916/fosdem_20_qczu0e8.pdf)). An hmdfs distributed filesystem also lives in the 5.10 tree ([kernel_linux_5.10](https://gitee.com/openharmony/kernel_linux_5.10)) (**unverified** that it was forward-ported to 6.6).
- **HDF (Hardware Driver Foundation)** is a driver framework layered *on top of* Linux, not a replacement for Linux drivers or Device Tree. Its layers are: HDI (stable hardware APIs), HDF core (driver loading, device node management, service management, message mechanism, power management), OSAL (memory/lock/thread shims so the same driver code builds on LiteOS and Linux), platform drivers (I2C/SPI/UART bus APIs) and peripheral driver models. Drivers are declared in **HCS** (`device_info.hcs`) config files. The stated goal is "one-time development for multi-device deployment" across LiteOS and Linux. ([driver overview](https://gitcode.com/openharmony/docs/blob/master/en/device-dev/driver/driver-overview-foundation.md), [drivers_hdf_core README](https://gitcode.com/openharmony/drivers_hdf_core/blob/master/README.md)). Oniro's summary: HDF "does not replace the Linux Kernel or Device Tree; it abstracts the driver logic and service publishing" (FOSDEM 2026, slide 7).
- **HDI (Hardware Device Interfaces)** are the real HAL. Interfaces are written in a `.idl` language compiled by `hdi-gen` into C/C++ proxy/stub and IPC code; versioned `v1_0`, `v1_1`... with the rule that major-version changes break compatibility and minor versions are backward compatible. Implementations are `.so` libraries loaded by user-mode HDF hosts (`uhdf2`: `hdf_devmgr` manager, `hdf_devhost` host processes) and declared in HCS. Interface families: audio, camera, codec, display, format, input, misc, sensor, USB, WLAN. ([drivers_interface README](https://gitcode.com/openharmony/drivers_interface/blob/master/README.md), [uhdf2](https://gitcode.com/openharmony/drivers_adapter/tree/master/uhdf2))
- **Graphics**: the Display HDI wraps Linux DRM/KMS for modesetting and vsync; the memory HDI wraps Gralloc/GBM; buffers are shared as DMA-BUF. On top sits **Rosen**, a retained-mode scene-graph compositor: the app builds an RSNode tree in-process, batches updates into IPC transactions, and a central Render Service rebuilds the scene and runs the "UniRender" pipeline to composite frames (FOSDEM 2026 slides 8-9; [graphic_graphic_2d README](https://gitcode.com/openharmony/graphic_graphic_2d/blob/master/README.md)). Rendering engine is a Skia-derived 2D library (**from memory, not re-verified**).
- **Vendor blobs**: OpenHarmony uses **musl** libc. Mobile SoC vendors ship Bionic-linked Android blobs, so Oniro had to adopt **libhybris** exactly as Halium/UBports do. On the OnePlus 6T (SDM845) they used mainline + Freedreno/Mesa and ALSA (alsa-lib) behind the HDF audio HAL; on the Volla X23 (MediaTek) they only reached boot + DRM display + touch, with GPU/Wi-Fi via libhybris still in progress. Quote from slide 11: "Workaround, not ideal: Binary blobs remain a black box." ([FOSDEM 2026](https://archive.fosdem.org/2026/events/attachments/SYBWKY-bringing_openharmony_to_phones_lessons_from_the_oniro_porting_effort/slides/266916/fosdem_20_qczu0e8.pdf), [FOSDEM 2025 notes](https://publish.obsidian.md/common-knowledge-scout/civil/events/Europe/FOSDEM+2025/en/FOSS+on+Mobile+Devices+11/Bringing+Oniro+to+Mobile+Challenges+in+Hardware))

### 1.3 Kernel strategy: what HarmonyOS NEXT actually ships

HarmonyOS 5 (NEXT, stable 2024-11-26) and HarmonyOS 6 (stable 2025-11-25) run the **HongMeng kernel (HM)**, a closed-source microkernel. The OSDI'24 paper by Haibo Chen et al. is the only serious technical source ([paper](https://www.usenix.org/conference/osdi24/presentation/chen-haibo)). Key facts from it:

- Core kernel is ~90k LoC of C (scheduler, timers, access control); OS services (process/memory manager, FS, drivers) are >1M LoC and run as isolated services. Three **isolation classes**: IC0 (in core TCB; in phones only the Linux ABI shim), IC1 (kernel-space but mechanism-isolated via ARM watchpoints / Intel PKS, with CFI), IC2 (address-space isolated user space). On phones, process/memory manager, FS and native drivers are placed at IC1; the Linux driver container and non-critical services at IC2.
- **Linux ABI compatibility** through an in-kernel "ABI-compliant shim" that redirects Linux syscalls to services and keeps centralized state (fd table) so `poll`, `fork` and vectored `ioctl` work. HM passes AOSP CTS/VTS. Some apps that depend on undocumented Linux behavior still fail.
- **Linux Driver Container (LDC)**: unmodified Linux drivers run in a user-space container built from a trimmed Linux runtime ("DC-base", derived from LTS 4.4/4.19/5.10, <100 changes to move 4.19->5.10). For performance-critical drivers (UFS), a "twin driver" splits control plane (in LDC) from data plane (native, IC1). Over 700 Linux drivers were reused this way, "including all the needed ones for smartphones" (camera, display, audio, NPU/GPU, storage).
- Reported results on Kirin 9000: 17% shorter app cold start (geomean), 19% lighter instruction load, 10% fewer frame drops, 10%/65% lower video/audio interrupt latency vs. tuned Linux 5.10. `fork` and `clone` are 2x slower than Linux.
- Certification: CC EAL6+ (2023) and ASIL-D; critical components are "semi-formally verified" ([Wikipedia: HongMeng Kernel](https://en.wikipedia.org/wiki/HongMeng_Kernel)).

OpenHarmony has **not** adopted HM; its standard system is still Linux. The microkernel is therefore an engineering achievement you can learn from but cannot download.

### 1.4 Application model (Stage model) and languages

- **Stage model** (API 9+, replacing the older FA model): one `AbilityStage` per HAP in a process; `UIAbility` (Activity-like, lifecycle Create/Foreground/Background/Destroy), each bound to a `WindowStage`; `ExtensionAbility` subclasses for typed extension points whose lifecycle the *system* manages: `FormExtensionAbility` (widgets), `InputMethodExtensionAbility`, `WorkSchedulerExtensionAbility`, and since 6.0 `AppServiceExtensionAbility`. UIAbilities run in the app's main process; some extensions (e.g. Form) run in separate processes and separate sandboxes (`+extension-<module>-<name>+<bundle>` directories). ([Stage model overview](https://gitcode.com/openharmony/docs/blob/master/en/application-dev/application-models/stage-model-development-overview.md), [6.0 release notes](https://gitcode.com/openharmony/docs/blob/master/en/release-notes/OpenHarmony-v6.0-release.md))
- **ArkTS** is a TypeScript superset with static-typing restrictions, compiled by **ArkCompiler** to `.abc` bytecode and run by the Ark runtime (interpreter, inline caches, PGO-driven AOT; CMS + partial-compacting GC; actor-style concurrency via TaskPool/Worker/Sendable, no shared heap). Since 6.0 there are two runtimes: ArkTS-Dyn (dynamic typing at runtime) and ArkTS-Sta (static typing, "ArkTS 1.2"). Apache-2.0. ([ArkTS runtime overview](https://gitcode.com/openharmony/docs/blob/master/en/application-dev/arkts-utils/arkts-runtime-overview.md), [ets_runtime overview](https://gitcode.com/openharmony/arkcompiler_ets_runtime/blob/master/docs/overview.md), [Wikipedia: ArkTS](https://en.wikipedia.org/wiki/ArkTS))
- **ArkUI** is a declarative UI framework (`@Component struct`, `@State`, builder chains) on top of Rosen. **ArkUI-X** ports it to Android/iOS (Apache-2.0; community consensus "not yet mature") ([ArkUI-X overview](https://gitcode.com/arkui-x/docs/blob/master/en/ArkUI-X-Overview.md)).
- **Cangjie** is a second, from-scratch language (LLVM-based native compiler, concurrent GC) open-sourced 2025-07-30, 1.1.3 on 2026-05-29 ([Wikipedia: Cangjie](https://en.wikipedia.org/wiki/Cangjie_(programming_language))). ArkWeb is Chromium (132 LTS in HarmonyOS 6).

### 1.5 Distributed ("super device") stack

- **DSoftBus** has four modules: discovery (CoAP-based on LAN, BLE), networking (LNN, logical network), connection (WLAN, BR, BLE, Ethernet) and transmission (bytes, message, stream, file sessions). Constraints: devices must be **bound/authenticated first** (device_auth / HiChain group model), connections are LAN or near-field only, apps need `DISTRIBUTED_DATASYNC` permission. ([communication_dsoftbus README](https://gitee.com/openharmony/communication_dsoftbus/blob/master/README.md), [openEuler DSoftBus](https://www.openeuler.org/en/blog/20220722-embedded-fenbushi/fenbushi.html)). Notably it has been built on **openEuler** (glibc Linux), proving it is not OpenHarmony-only.
- On top: distributed data management (distributed KV store, RDB, Distributed Data Object, UDMF), distributed scheduler (remote start / migrate a UIAbility), distributed hardware (device_manager plus virtual camera/screen/audio), and hmdfs for files. "Super Device" is Huawei's brand name for this bundle.

### 1.6 Sandbox and permissions

- **Per-app mount-namespace sandbox**: the app sees `/data/storage/el1/bundle`, `el1/base`, `el2/base`, `el2/database`, `el2/distributedfiles`, mapped to `/data/app/el2/<USERID>/base/<BUNDLE>`. **Encryption levels EL1-EL5** tie file keys to lock state: EL1 available from boot, EL2 after first unlock (default), EL3/EL4 inaccessible while locked, EL5 special. ([app sandbox](https://gitcode.com/openharmony/docs/blob/master/en/application-dev/file-management/app-sandbox-directory.md))
- **SELinux** type enforcement with four subject classes (native, app, SA = system ability, HDF process); app process and data labels derive from the app's APL. ([SELinux overview](https://gitcode.com/openharmony/docs/blob/master/en/device-dev/subsystems/subsys-security-selinux-overview.md))
- **AccessTokenManager (ATM)**: every app gets a 32-bit TokenID carrying APP ID, user ID, clone index, **APL** (`normal` / `system_basic` / `system_core`) and granted permissions; services verify callers by TokenID (kernel-visible via `CONFIG_ACCESS_TOKENID`). Permissions are `system_grant` or `user_grant`; "restricted" permissions need an **ACL** entry approved at store review. Scoped one-shot access is done with **Pickers and security components** (e.g. a photo picker grants one photo, not the gallery). ([security_access_token README](https://gitcode.com/openharmony/security_access_token/blob/master/README.md), [access control overview](https://gitcode.com/openharmony/docs/blob/master/en/application-dev/security/AccessToken/access-token-overview.md))
- HarmonyOS NEXT (closed) adds: locked bootloaders on all devices, and sideloading only of HAPs signed with Huawei-issued developer certificates chaining to Huawei's root CA ([Promon analysis](https://promon.io/security-news/harmonyos-next)).

## 2. What it does well

1. **A real, versioned HAL contract (HDI) with generated IPC.** The `.idl` -> proxy/stub -> isolated host-process pattern, with explicit major/minor compatibility rules and ten interface families, is a cleaner, smaller version of Android's HIDL/AIDL. It is what let Oniro treat ALSA, Mesa and libhybris as interchangeable backends behind the same audio/display HDI.
2. **Honest engineering on the microkernel (HarmonyOS side).** The OSDI paper's lessons are unusually candid: "Compatible first, then nativize gradually"; "Specification alone is insufficient. Examine compatibility via large-scale testing"; isolation classes instead of dogmatic user-space-everything; reuse >700 unmodified Linux drivers in containers. That is the strongest evidence anywhere that *driver reuse through a Linux runtime container* works at phone scale.
3. **Scoped, revocable data access as a first-class UX pattern.** Pickers/security components plus EL1-EL5 encryption classes and TokenID-based authorization give a coherent least-privilege story that Android only reached piecemeal.
4. **Typed extension points with system-owned lifecycle** (ExtensionAbility subclasses, out-of-process by type). This is better factored than Android's Service/BroadcastReceiver mix.
5. **Retained-mode compositor with client scene graphs** (Rosen). Batching scene-graph diffs over IPC instead of raw buffers per view is the same insight as Flutter's layer tree and Apple's Core Animation, applied at the system compositor level.
6. **One distributed-communication primitive** (DSoftBus) that normalizes discovery/auth/session across Wi-Fi, BLE and Ethernet, and is portable (runs on openEuler).
7. **Release cadence and conformance.** Twice-yearly releases on a published roadmap (5.0.2 -> 5.0.3 -> 5.1 -> 6.0 Beta -> 6.0 -> 6.1 -> 7.0 Beta), API levels, XTS test suites and an OpenAtom compatibility certification program ([roadmap](https://gitcode.com/openharmony/release-management/blob/master/OpenHarmony-RoadMap.md)).
8. **Ecosystem bootstrapping via existing frameworks** (Oniro): React Native for OpenHarmony, Ionic Capacitor, Tauri, Lynx, Servo; a QEMU x86_64 emulator with Mesa for CI; a VS Code extension instead of a mandatory proprietary IDE.

## 3. What it does badly / lessons learned

1. **Access friction.** The primary forge (GitCode) throttles anonymous reads ("访问频次受限，请登录"), docs are Chinese-first, and Oniro's reason for existing is literally "GitHub mirrors with daily synchronization, English-first documentation" (FOSDEM 2026, slide 3). The Gitee -> GitCode move (2025-09-15) broke links again.
2. **Kernel fork tax.** Binder, ashmem (still, in 2026), HDF, access-token and RTG patches mean OpenHarmony needs its own 5.10/6.6 trees. On phones you inherit the vendor kernel *and* must backport these patches to it.
3. **musl vs. Bionic.** Choosing musl made every Android blob a libhybris problem; Oniro calls its own solution a "workaround, not ideal". Halium/UBports hit the same wall with glibc, so this is not avoidable, but musl adds extra symbol/ABI friction.
4. **"Unified driver model" is thin on the standard system.** On Linux, HDF is a user-space service framework plus a kernel patch; the actual device drivers are Linux drivers or vendor blobs. The multi-kernel abstraction (KAL/OSAL) buys portability to LiteOS, which a phone OS does not need.
5. **Language and toolchain lock-in.** ArkTS + ArkCompiler + Cangjie + DevEco Studio is a multi-thousand-engineer investment that produced a 2025 ecosystem of ~100k native apps only because Huawei could mandate it in China. Third parties (Oniro) are actively routing around it with React Native, Tauri and Lynx.
6. **Closed crown jewels.** The microkernel, driver containers, and HarmonyOS NEXT's device layer are closed; HarmonyOS phones have locked bootloaders and require Huawei-signed certificates even to sideload. The open project cannot run on any Huawei phone.
7. **Governance is nominally neutral but Huawei-dominated**; the May 2025 mass-"please support OpenHarmony" issue campaign on dozens of GitHub repos was widely received as spam ([Xataka Móvil](https://www.xatakamovil.com/sistemas-operativos/huawei-queria-colaboradores-para-su-nuevo-sistema-operativo-su-forma-buscarlos-termina-acusaciones-spam)).
8. **Distributed features need an account/trust fabric.** DSoftBus sessions require pre-bound devices; the rich "super device" demos presuppose many Huawei-account devices. Outside that, the feature is a demo.
9. **Fragmentation.** 30+ OpenHarmony distributions (KaihongOS, HiHopeOS, Orange Pi OS, MineHarmony, SwanLinkOS, Midea IoT OS...) and essentially zero non-Huawei phones shipping it.

## 5. Borrowable ideas for a new Linux-based phone OS

Concrete, with licenses. Ordered by how much a one-developer, Go/Python/TypeScript-leaning team can realistically lift.

1. **HDI-style versioned HAL IDL (pattern, not code).** Define every hardware service (display, audio, camera, sensors, modem, Wi-Fi) as a versioned interface in an IDL, generate client/server stubs, and run each implementation in its own sandboxed host process. Backends can be libhybris-wrapped Android HALs today and mainline/Mesa/ALSA/ModemManager tomorrow. On Linux the natural transports are **Varlink** (simple, Go/Python/Rust bindings, used by systemd) or **D-Bus with XML introspection**; adopt HDI's `v1_0` major/minor compatibility rule verbatim. OpenHarmony's actual `drivers_interface` `.idl` files (Apache-2.0) are a good checklist of which methods a phone HAL needs.
2. **Reuse DSoftBus itself or clone its semantics.** `communication_dsoftbus` is Apache-2.0 C and already builds on openEuler (glibc). Even if you do not vendor it, copy the API shape: discover -> bind/auth -> open session of type {bytes, message, stream, file} over whatever link exists. A modern re-implementation would use DNS-SD/mDNS + BLE advertising for discovery, a Noise/TLS 1.3 pairing with device certificates for binding, and QUIC for sessions. This gives you KDE-Connect-class continuity with one API.
3. **CRDT-based distributed data instead of OpenHarmony's KV sync.** Their distributed KV store / Distributed Data Object is the right product idea; implement it with **Automerge** or **Loro** (MIT) over the session layer above. That is a genuinely newer technology than anything in OpenHarmony.
4. **EL1-EL5 data classes.** Implement with Linux **fscrypt** on ext4/f2fs: a boot-available policy (EL1), a user-unlock policy (EL2, default), and a lock-evicted policy (EL4) whose keys are removed from the keyring on lock. Expose them as fixed sandbox paths like `/data/storage/el2/base` so apps cannot get it wrong.
5. **Picker / security-component access model.** On Linux this already exists as **xdg-desktop-portal** (FileChooser, Camera, Location, ScreenCast). Make portals the *only* way to reach user data, as OpenHarmony does with Pickers, rather than an optional Flatpak nicety.
6. **TokenID-style caller identity.** Every system service should authorize by a stable app identity carried on the connection, not by UID. On Linux: give each app a cgroup + AppArmor/SELinux label at launch (snapd/Flatpak already do this), pass identity via `SO_PEERCRED`/`pidfd`, and keep one permission service (ATM equivalent) that answers "does token T hold permission P" with persisted user grants. Three APLs (normal / system_basic / system_core) plus a store-reviewed ACL for restricted permissions is a sane policy model.
7. **Typed extension points with system-owned lifecycle.** Map ExtensionAbility kinds onto **systemd user services with D-Bus activation** and per-kind sandboxes: widget provider, input method, share target, background scheduler, notification listener. The borrowable part is the rule that the system, not the app, decides when these processes exist.
8. **Scene-graph compositor.** You will still want a Wayland compositor on a Linux phone, but Rosen's client-side node tree + batched transactions is the architecture to copy if you build a UI toolkit: ship a retained scene graph to the compositor rather than per-widget buffers. In Rust this is close to what **Smithay** + a scene API or **Servo**/`wgpu` enable; in Qt it is the Qt Quick scene graph. (Evaluate against the earlier Qt6/QML suggestion on merit; Rosen validates the general approach, not Qt specifically.)
9. **Grow apps through existing frameworks, not a new language.** Oniro's choices are the model: React Native (Huawei maintains `react-native-harmony`), Capacitor/Ionic, Tauri, Lynx (ByteDance, Apache-2.0), Flutter and Kotlin Multiplatform "under research". For a Linux phone this means first-class Flutter, Tauri/WebView and a maintained GTK4/Qt6 path, with Wayland and portals as the stable ABI.
10. **CI emulator first.** Oniro's QEMU x86_64 image with Mesa software/virtio-gpu rendering enabled IDE integration and CI before any phone booted. Do the same with a `virt` machine type and virtio-gpu; it is also how you attract contributors without hardware.
11. **HarmonyOS's microkernel lessons, applied to Linux.** You cannot have HM, but you can adopt its deployment lessons: treat vendor blobs as an untrusted "driver container" (run libhybris-backed HAL hosts under seccomp/AppArmor with minimal mounts), separate control and data planes so the hot path stays native, and *measure* compatibility with a large test corpus (their CTS/VTS use) rather than specifying it.
12. **A conformance suite and compatibility mark from day one** (OpenAtom's XTS/compatibility working group). Even a small `xts`-like test pack that device ports must pass is what keeps a multi-device project coherent.
13. **Kernel feature list as a port spec.** Publish the exact `CONFIG_*` and patch set a vendor kernel must carry (as Oniro did on one slide). Keep it short: Halium/UBports experience plus OpenHarmony's list says binder, ashmem/memfd, cgroup v2, fscrypt, and nothing proprietary.

Licenses: OpenHarmony code is Apache-2.0 (Linux kernel patches GPL-2.0; LiteOS kernels BSD-3-Clause **from memory, verify**); ArkTS/ArkCompiler/ArkUI/ArkUI-X Apache-2.0; Cangjie open source (license not stated on its site, **verify** on gitcode.com/Cangjie); HongMeng kernel and HarmonyOS NEXT proprietary; Oniro deliverables Eclipse Foundation (EPL-2.0/Apache-2.0 **unverified** per component).

## 6. Pitfalls to avoid

1. **Do not invent a language or runtime.** ArkTS/ArkCompiler/Cangjie needed Huawei-scale staffing and a captive market. A one-person project should pick TypeScript (via Tauri/Capacitor/Lynx), Dart (Flutter), Rust or Go, all with AOT or JIT already solved.
2. **Do not carry a mandatory kernel patch set.** OpenHarmony still cannot boot vanilla mainline in 2026 and still depends on ashmem. On current phones you are already stuck with a vendor kernel; do not add your own out-of-tree requirements on top.
3. **Do not pick musl if you depend on libhybris.** Oniro's extra Bionic-vs-musl friction is self-inflicted; Halium's glibc path is better-trodden. (If you do not use blobs at all, musl is fine, but then you are back to 3-6-year-old mainline devices.)
4. **Do not build multi-kernel abstraction layers (KAL/OSAL) for device classes you will never ship.** Phones only.
5. **Do not host on a login-walled forge or write Chinese-first docs** if you want contributors; Oniro's whole value proposition is undoing that mistake.
6. **Do not gate sideloading behind your own certificate authority** (HarmonyOS NEXT) and do not require locked bootloaders; that kills the hobbyist base you need.
7. **Do not sell "super device" before you have a trust/pairing fabric.** DSoftBus without bound devices is nothing; ship pairing and one killer flow (clipboard/file/notification continuity) first.
8. **Do not mistake HDF for a way to avoid vendor drivers.** On the Linux standard system it is a service framework; the drivers are still Linux drivers or blobs. Plan Halium/libhybris or mainline, exactly as the rest of the conversation already concluded.
9. **Do not copy the fragmentation**: one reference image, one API level, one conformance suite, and downstream "distributions" only after that exists.
10. **Do not trust vendor device counts or "third-largest mobile OS" claims** as evidence of phone adoption; outside Huawei there are no shipping OpenHarmony phones as of this date (Volla X23 images are developer previews).
